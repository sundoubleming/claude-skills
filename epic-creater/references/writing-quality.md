# 逐节写作判据

用于填写和评审 Epic 文档。每节列出「合格的样子」与「常见的失分写法」。

## §1 背景与业务价值

**合格**：
- 现状写清「当前用哪个接口 / 哪张表 / 哪段流程」，引具体路径
- 痛点带影响面：哪类用户、多大规模、多高频率
- 不做的后果具体：业务损失、安全风险、技术债累积速度、合规不满足

**失分**：
- 只写「我们要支持 X」，没写现状怎么做的
- 痛点没有量化，无法据此判断优先级
- 完全新功能却不说明需要支持的业务场景
- 过于详细的描述问题原因，贴代码等

## §2 目标与非目标

**合格的目标**：交付后可观测、可度量的结果。
> ✓ 「管理员开启开关后，LLM资源配置会在30s内生效」
> ✓ 「用户可以通过Claude接口成功访问配置的LLM资源」

**不合格的目标**：简单的功能支持描述，代码改动
> ✗ 「支持动态路由开关」——这是功能，不是目标
> ✗ 「支持/v1/responses接口」——这是代码改动，不是目标

**合格的非目标**：**每条都有理由**，说明为什么不做。只写「暂不支持」不给理由，等于没写。
> ✓ 「不修改当前的判断是否要重试的逻辑。本Epic的重点在于选路，与重试逻辑无关。」
> ✓ 「不修改管理员配置的优先级。管理员配置的优先级是第一配置，不能动态修改。」

## §3 关键决策

**合格**：编号 D1/D2/...，五行齐全——决策点、选择、理由、被否决的方案及原因(如果没有被否决方案则可以省略)。
这里只讨论流程逻辑，不讨论算法，数据结构或者其他具体实现的内容。

**不合格**：
- 把未拍板的事项混进来（应放 §10 未决项）
- 只写结论不写理由，Story 评审时会重新讨论一遍
- 决策分散在正文各处，无法被子文档引用
- 具体要使用的数值，算法或数据结构

| 决策点 | 选择 | 理由 | 被否决的方案及原因 |
| ------ | ---- | ---- | ------------------ |
| ✓ 多个数据面实例的数据聚合方法| 每个数据面实例的数据不共享，由控制面轮询获取并聚合。| 简单，控制面不需要额外增加其他中间件的访问。 | 通过Redis聚合：控制面需要额外访问Redis。 |
| ✓ 是否需要支持单个租户开关 | 需要 | 方便新功能出问题时回滚。 | 不需要：出问题时只能回退整个版本。 |
| ✗ 计算数据来源 | 每个数据面实例使用本地前5min的数据。| (**无理由**) | |
| ✗ 租户配置保存的位置(**不讨论具体的数据结构**) | 放在租户表中，增加一个字段 | 每个租户有各自的配置 |  |

## §4 范围边界

**合格**：范围内是清单；范围外是表格，含原因与归属；各模块改动一览标出「新增 / 扩展 / 无改动」。

模块改动一览同时决定需要哪些 Story、需要跑哪些跨模块 E2E，别省。

## §5 总体设计

先写一段文字说明整体思路与术语，再进小节。术语口径需与项目术语表一致；本 Epic 新引入的术语应同步收口到术语表。

**失分**：
- 把设计文档全文塞进来。判断方法：**如果某段内容能让工程师直接复制到代码里，它就该去 Story。**
- 把讨论的内容和已经被否定的方案完整，详细地写入。**如果需要说明某个方案或者做法不可行，简单说明理由即可**

### §5.1 整体流程总览
通过泳道图或者流程图的形式从系统各个模块的角度描述该需求的实现方法。如果比较简单也可以使用文字。

**合格**：
- 逻辑清晰，并且能够完成功能需求。
- 明确清晰完整地描述业务的数据流，包括数据的交互及每个模块的作用等。
- 对处理分支有明显标识，无遗漏重要分支或异常场景。

**不合格**：
- 异常场景无处理，使得实现时也遗漏或者需要重新讨论。
- 出现无关的组件或逻辑，增加文档的复杂程度。
- 不满足 §2 目标与非目标 中的目标。
- 描述了 §2 目标与非目标 中的非目标的实现。
- 节点过于细致，有代码中变量相关的描述或计算。

### §5.2 数据模型变更
明确本次改动需要新增/修改的中间件表或运作中涉及的Redis Key等，有其他中间件相关的数据模型/Topic也需要在这里补充。

**合格**：
- 明确涉及的组件(SQL/Redis等)，数据字段名称，类型，其他元数据及用途等。
- 如果是SQL，需要给出建表或者建列语句。

### §5.3 数据模型变更
明确本次改动需要新增/修改的对外或者内部组件之间的接口。

**合格**：
- 对于修改的接口，要明确，完整地给出修改的内容或字段。
- 对于新增的接口，要完整地给出接口路径，请求/响应头，请求响应体定义及用法。

**不合格**：
- 接口描述不清晰，缺少方法，路径或者url参数等。

## §6 架构影响评估

**合格**：逐项回答，**无影响也显式写「无影响」**，不留空——留空意味着没评估过。

- 分层架构：逐层标明是否新增/修改。
- 跨层访问：有则说明原因与替代方案，无则写「无跨层访问」。
- 新增线程或定时器：有则说明功能及影响。
- 中间件：是否新增中间件，新增须说明必要性
- 性能与容量：给数字和量级，不给「性能良好」
- **回滚方案必须是具体动作**，不是「回滚版本」四个字
- 需同步更新的文档列成 checklist

**失分**：写「不涉及」「影响较小」这类无法验证的表述。

## §7 Story 拆分

**合格**：表格五列——Story 编号、标题、负责模块、负责工种、前置 Story。
每个 Story 只写一句话目标，详细设计在子文档目录下。

**失分**：在 Epic 里展开 Story 的详细设计，导致 Story 文档被架空。

### §7.x Story 描述
每个开发 Story 单独一个小节（§7.1、§7.2 …，标题形如「### 7.1 Story {N}.1：{标题}」），测试 Story（`t` 后缀）只在 §7 表格中列出，不写描述。
每个小节依次包含四部分：用户故事、目标、核心、验收。

**用户故事**：`As a {角色} / I want {操作意图} / So that {获得的价值}` 三行齐全。
> ✓ 「As a 平台管理员，I want 给用户充值额度，So that 用户可以使用平台提供的 API KEY」
> ✗ 「As a 开发者，I want 实现令牌表，So that 完成令牌功能」——角色不是业务角色，意图是开发动作，价值是同义反复

- 角色是系统中真实存在的业务角色（平台管理员、租户管理员、租户用户等），与 §5 术语一致，不写「开发者」「系统」
- I want 写角色的操作意图，不写实现动作
- So that 写角色得到的业务价值，不能是 I want 的复述

**目标**：列出该 Story 交付后带来的效果，每条以「维度：效果」的形式书写（如「安全管控：令牌精确到用户」）。
- 目标需能追溯到 Epic §2.1 的某个 G 编号，不能超出 Epic 目标范围，也不能落入 §2.2 非目标
- 写效果，不写功能清单或代码改动（判据同 §2）

**核心**：列出该 Story 需要交付的能力，**只写能力，不写实现细节**。
> ✓ 「租户管理员可以给租户用户分配、禁用数据面令牌」
> ✓ 「租户用户可以重新生成数据面令牌密钥」
> ✗ 「新增 `dp_token` 表，含 `user_id`、`status` 字段」——表名、字段属于 §5.2 与 Story 文档
> ✗ 「新增 `POST /api/v1/tokens/assign` 接口」——接口路径属于 §5.3 与 Story 文档

- 不出现表名、字段名、接口路径、类型、方法签名
- 各 Story 的核心合起来应覆盖 §4 中标为「新增 / 扩展」的模块改动，不同 Story 之间不重复

**验收**：Story 级验收条目，严格使用一行一条的 `WHEN {触发条件} THEN {可观测结果}` 格式，不写成散文。
- **每条目标至少对应一条验收**——目标无验收，等于无法判断是否达成
- **必须覆盖异常场景**——除正常路径外，至少包含一条失败/边界场景（如无权限、对象已禁用、重复操作）
- **THEN 必须可观测**——写出能直接验证的结果（返回什么、看到什么、数据如何变化），不写「功能正常」「配置正常」「符合预期」

> ✓ 「WHEN 租户管理员给租户用户分配令牌 THEN 该用户在令牌列表中立即可见该令牌，状态为启用」
> ✓ 「WHEN 租户用户使用已禁用的令牌访问数据面 THEN 请求被拒绝并返回令牌已禁用的错误码」
> ✓ 「WHEN 租户用户获取新的令牌密钥 THEN 返回新生成的随机密钥，且数据表中不保存该密钥明文」
> ✗ 「WHEN 分配令牌给租户用户 THEN 配置正常」——「配置正常」无法验证
> ✗ 「分配令牌后用户应该能正常使用」——不是 WHEN/THEN 格式

**失分**：
- 用户故事缺少 So that，或角色、意图写成开发视角
- 核心里写了表结构、接口路径等实现细节
- 验收只覆盖正常路径，或某条目标没有对应验收
- THEN 结果模糊，无法据此编写测试用例

## §8 Story 依赖关系图

mermaid 即可。作用是暴露关键路径，不是画得好看。

## §9 风险与缓解

**合格**：每行六列齐全——风险、影响、概率、缓解措施、**触发后的回滚动作**。

**失分**：
- 缓解措施写「加强测试」「注意监控」——不是措施
- 缺少回滚动作列，出问题时无从下手

## §10 未决项

**合格**：每项有 Owner 和截止时间，并写清不确认会阻塞什么。
无未决项时写「无」——但写「无」前先自查，通常至少有一两项。

## §11 验收准则

区分 Epic 级与 Story 级。分六类：功能、性能、兼容性、安全与合规、E2E、工程。
- 功能验收项对应 §2.1 的目标编号，形成闭环
- 性能必须给数字（延迟增量、吞吐、资源占用）
- E2E 列出具体脚本路径
- 工程验收给出构建与测试命令

## §12 配套文档

指向 Story 目录、Task 目录、接口定义、架构文档、E2E 脚本。
如果子文档目录是空的，说明 Epic 写了但没拆——这一节能暴露该断裂。

## 通用失分模式

1. **贴实现代码**——结构体定义、建表 SQL、脚本全文、方法签名。破坏层级分工，且会被当成权威设计复制到多个 Story。
2. **目标写成功能清单**——无法判断做没做到。
3. **非目标和范围外省掉**——后续范围蔓延无处追责。
4. **回滚方案空泛**——出问题时才发现没预案。
5. **章节不统一**——同一文档库里多种开头写法、全角半角混用，导致无法自动校验、无法扫读。
6. **讨论细节处理失当**——讨论中确认的代码 / 数据层约束要么塞进正文（违反 1），要么直接丢掉（Story 阶段被重新讨论）。正确做法是写进【待下沉】注释，标明目标 Story，详细设计文档写完后迁移并删除。
