# Epic PRD 文档生成

按统一模板产出 Epic 文档：落地骨架、逐节引导填写。适用于任何采用「Epic → Story → Task」分层文档体系的项目。

## 零、目录约定

固定使用工作目录下的 `prd/`，**不依赖任何配置文件**：

```
./prd/                          Epic 文档目录，不存在时自动创建
./prd/epic-{N}-{slug}.md        生成的 Epic 文档
./prd/_epic-template.md         模板，不存在时自动从技能自带模板复制
./stories/epic-{N}-{slug}/      仅当 ./stories/ 已存在时创建
./tasks/epic-{N}-{slug}/        仅当 ./tasks/ 已存在时创建
```

`stories/` 与 `tasks/` 是**可选**的：存在就按 Epic 一一对应建目录，不存在就跳过，不会主动创建。

需要换目录时用 `--dir` 参数，不要改动脚本默认值。

**编号规则**：取 `prd/` 下现有 Epic 的最大编号 + 1，仅此而已。**不做冲突检测、不做空缺补位、不管历史遗留的重号**——那些是独立的治理工作，不属于本技能。

### 模板

`prd/_epic-template.md` 是唯一权威模板。若不存在，脚本会自动从技能自带模板（`assets/epic-template.md`）复制一份过去。

**每次动手前都要重新读模板**——不要凭记忆复述内容，模板可能已被项目修改。章节速查见 `references/epic-structure.md`，逐节判据见 `references/writing-quality.md`。

项目首次使用时，问一下用户是否要先按项目情况调整模板（模块名、是否有 Story/Task 层级、验收命令），再开始写第一份 Epic。

## 一、判断意图

| 用户诉求 | 动作 |
|---------|------|
| 新建 Epic / 写 PRD | 走完整流程（二 → 四） |
| 补全已有 Epic 的缺失章节 | 跳到步骤三，只填缺的节 |
| 只看会分到几号 | `new_epic.py --dry-run`，不落盘 |
| 详细设计文档已写完，清理 Epic 暂存的细节 | 见「三、逐节填写 → 待下沉的设计细节」的迁移步骤 |

## 二、采集必要信息

**动手前必须拿到四项**，一次问全，不要为凑齐模板连问十几个问题：

- **slug**：小写短横线英文，如 `tenant-request-id-trace`
- **中文标题 / 英文标题**
- **要解决的问题**：现状是什么、谁受影响、不做的后果
- **涉及模块**：项目有哪些模块，本 Epic 改动哪些

然后建骨架：

```bash
python3 scripts/new_epic.py \
  --slug tenant-request-id-trace \
  --title "租户自定义请求头溯源" \
  --en-title "Tenant Request ID Trace"
```

常用参数：`--dry-run`（只报告不落盘）、`--dir path/to/prd`（换目录）。

目标路径已存在时脚本直接报错退出，不覆盖。

## 三、逐节填写

先建骨架，再逐节填。**只在遇到只有用户能拍板的决策时停下问**——范围取舍、优先级、兼容策略。

按模板顺序写，**把注释和 `{占位符}` 换成真实内容**，填完删掉全部 `<!-- -->` 注释（【待下沉】注释除外，见下文）。

- **[必备] 章节不得省略、不得留空**。无内容时写「无」并说明为什么无（如未决项写「无」、架构影响写「无影响」）。
- **[可选] 章节**按模板注释里的触发条件决定保留或整节删除。条件不满足就不要写，写了只是稀释信号。
- **不许贴实现代码**：不贴结构体定义、完整建表 SQL、脚本全文、方法签名。数据模型只列表名/字段/类型/约束/索引；接口只列 method + path + 用途。细节下沉到 Story。
- **区分 Epic 与 Story**：Story 只写「一句话目标 + 交付物 + 前置依赖」三件事，详细设计留给 `stories/`。
- 每填一节，对照 `references/writing-quality.md` 里该节的判据自查。最常见的失分点：目标写成功能清单、非目标不给理由、回滚方案写成「回滚版本」、风险缓解写成「加强测试」。

### 待下沉的设计细节

讨论中用户明确要求、但属于代码或数据层的细节（字段取值约束、建表/建列语句、缓存 value 结构、算法参数、关键方法的行为约定等），**不写进正文，也不丢弃**，就近写在相关章节末尾的【待下沉】注释里，暂存到详细设计文档（Story 文档）落地为止：

```
<!-- 【待下沉】→ Story {N}.{M}
  后续编写详细设计文档时，将本注释内容复制到详细设计文档中，并删除 Epic 中的本注释。
  关联：{§5.2 / D2 等}
  - {细节 1}
  - {细节 2}
-->
```

- 标记 `<!-- 【待下沉】` 固定不变，便于 grep；目标 Story 未定时写 `→ Story 待定`
- 只收**讨论中已确认**的细节；未拍板的进 §10 未决项，不要借注释绕过正文的「不许贴实现代码」
- 注释内不得出现 `-->`（mermaid 箭头会提前截断注释），需要时改写为 `→`
- 【待下沉】注释不计入正文行数与代码围栏数

**迁移**（详细设计文档写完后）：`grep -n "【待下沉】" prd/epic-{N}-*.md` 列出全部条目 → 逐条复制到目标 Story 文档对应章节 → 删除 Epic 中的该注释。若某条与 Epic 正文或 §3 决策冲突，先问用户以哪个为准，不要静默二选一。

篇幅控制在模板注释标明的区间内（默认 300–800 行）。写到上限还写不完，说明该拆 Epic 或该把细节移到 Story——**把这个判断告诉用户，而不是继续写**。

填完自查一遍：模板末尾的《提交前自检清单》逐条过，确认无 `{占位符}` 残留、除【待下沉】外无 `<!-- -->` 注释残留、[必备] 章节齐全。

## 四、收尾

若 `prd/README.md` 存在，它通常是项目的 Epic 索引，提醒用户同步一行（或直接帮他加）。索引不存在时不要主动创建。

交付时说明：创建了哪些文件、编号是多少、哪些 [必备] 章节是按假设填的需要用户确认、留了几条【待下沉】注释及各自的目标 Story。不要声称验证过而实际没做。
